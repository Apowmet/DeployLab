# Сценарий визуальной демонстрации (Windows 11 → Debian 13)

1. **GitHub → Clone.** Показать репозиторий, пустую рабочую папку, команду `git clone`, появление файлов.
2. **Visual Studio.** Открыть `DeployLab.csproj`, показать Solution Explorer и запуск через профиль HTTP; поставить breakpoint в `Program.cs` на `/health`.
3. **VS Code.** Открыть тот же каталог; показать `Program.cs`, `wwwroot`, терминал.
4. **До / после изменения сайта.** Заменить в `wwwroot/index.html` главный заголовок `От исходного кода` на `От GitHub до Linux` и обновить страницу. Для доклада подготовить скриншоты ДО и ПОСЛЕ.
5. **Компиляция.** Показать `dotnet build`, каталог `bin/Debug/net10.0` и разницу между исходниками и DLL.
6. **REST API.** Открыть `/health` через кнопку на сайте и через `curl`; объяснить JSON и HTTP 200.
7. **Runtime и ОС.** На Windows `/api/info` покажет Windows; снять скриншот блока Environment.
8. **Публикация.** Выполнить `dotnet publish -c Release -f net10.0 -r linux-x64 --self-contained false -o ./publish-linux`; показать дерево артефактов. Это **framework-dependent** развёртывание.
9. **Debian до.** `cat /etc/os-release`, `dotnet --info` (отсутствует) — отличный кадр БЫЛО.
10. **Debian после.** Установить ASP.NET Core Runtime 10, `dotnet --list-runtimes` — кадр СТАЛО.
11. **SSH/SCP.** Перенести артефакты и запустить приложение `dotnet DeployLab.dll --urls http://0.0.0.0:5000`.
12. **Проверка.** С Windows открыть `http://192.168.3.128:5000` и увидеть Linux вместо Windows.
13. **Мониторинг.** `curl -i http://127.0.0.1:5000/health`, затем настройка systemd и `journalctl` — отдельный этап лабораторной.
14. **CI/CD.** Показываем схему автоматизации уже проделанных вручную действий.

## Файлы для кадров

- Исходный код: `Program.cs`, `DeployLab.csproj`.
- HTML и CSS: `wwwroot/index.html`, `wwwroot/styles.css`.
- Артефакты: `publish-linux/` (не коммитить в Git).
- Сравнение систем: скриншоты `/api/info` на Windows и Debian.
- Ошибка/исправление: отсутствие `dotnet`, затем установленный ASP.NET Core Runtime.

## Важно для VM

`192.168.3.128` — текущий адрес по пользовательскому выводу; он может измениться после перезагрузки DHCP. Два адреса `172.17.0.1` и `172.18.0.1` относятся, вероятно, к виртуальным/контейнерным интерфейсам, для подключения к VM сначала пробуем `192.168.3.128`. Прежде чем открывать порт наружу, ограничить доступ доверенной локальной сетью.
